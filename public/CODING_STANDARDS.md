# 所有编码行为规范

本文件用于减少 AI 编程过程中常见的错误行为。

这些规则应该与具体项目要求结合使用。

**核心原则：**
宁愿谨慎地分析和确认，也不要快速进行错误或过度设计的实现。

对于非常简单的任务，请根据实际情况灵活判断。

---

# 1. 编码前先思考（Think Before Coding）

**不要猜测。不要隐藏不确定性。主动说明假设和权衡。**

在开始实现代码之前：

- 明确说明你的理解和假设。
- 如果需求存在不确定性，先询问，不要自行决定。
- 如果一个问题存在多种解释，列出不同方案，并说明区别。
- 如果存在更简单的方法，主动提出。
- 如果当前需求不清晰，暂停编码，指出具体疑惑并请求澄清。

禁止：

- 在没有确认需求时直接大规模修改代码。
- 假设用户没有说明的功能需求。
- 为不存在的问题提前设计复杂方案。

---

# 2. 优先保持简单（Simplicity First）

**用最少的代码解决明确的问题，不进行预测性设计。**

遵循：

- 不添加用户没有要求的功能。
- 不为一次性使用代码创建复杂抽象。
- 不添加没有实际需求的配置项。
- 不为了未来可能发生的情况设计复杂扩展。
- 不处理理论上不可能发生的异常情况。

如果：

```
200行代码可以解决的问题
```

可以优化为：

```
50行代码解决
```

应该重新设计。

每次编码前询问自己：

> 一个经验丰富的高级工程师看到这个实现，会不会认为它过度复杂？

如果答案是：

> 会

那么应该简化。

---

# 3. 精准修改（Surgical Changes）

**只修改必要内容，不进行无关重构。**

修改已有代码时：

不要：

- 顺便优化附近代码。
- 修改无关的注释。
- 调整无关格式。
- 重构没有问题的代码。
- 按自己的偏好改变已有代码风格。

应该：

- 遵循当前项目代码风格。
- 优先保持已有架构。
- 最小范围修改。

如果发现：

- 无关的废弃代码。
- 潜在问题。
- 可以优化的位置。

请：

> 提醒用户，但不要主动删除或修改。

---

## 关于代码清理

如果你的修改导致：

- import 不再使用。
- 变量变成无用变量。
- 函数没有调用。

可以删除：

> 仅删除由你的修改产生的无用内容。

不要删除：

- 原本存在的旧代码。
- 用户没有要求处理的代码。

---

## 修改原则：

每一行改变的代码，都应该能够直接追溯到：

> 用户当前提出的需求。

如果无法解释为什么修改这一行：

不要修改。

---

# 4. 目标驱动执行（Goal-Driven Execution）

**明确成功标准，并持续验证结果。**

不要只关注：

> "把代码写出来"

而应该定义：

> "如何证明这个任务完成"

例如：

---

需求：

```
添加输入验证
```

应该转换为：

```
1. 编写非法输入测试
2. 实现验证逻辑
3. 确认测试通过
```

---

需求：

```
修复 Bug
```

应该转换为：

```
1. 编写能够复现 Bug 的测试
2. 修改代码
3. 确认测试通过
```

---

需求：

```
重构模块
```

应该转换为：

```
1. 修改前运行测试
2. 完成重构
3. 修改后确认所有测试通过
```

---

# 5. 多步骤任务执行规范

对于复杂任务，先给出简短计划：

格式：

```
执行计划：

1. [任务步骤]
   验证方式：[如何确认完成]

2. [任务步骤]
   验证方式：[如何确认完成]

3. [任务步骤]
   验证方式：[如何确认完成]
```

完成每一步后：

- 检查结果。
- 验证是否符合目标。
- 再进入下一步。

---

# 6. 不要过度推断用户需求

如果用户说：

```
增加登录功能
```

不要自动添加：

- 权限系统
- OAuth
- 多语言
- 数据分析
- 用户等级

除非用户明确要求。

---

# 7. 修改代码前先理解项目

开始修改之前：

必须先了解：

- 项目目录结构。
- 技术栈。
- 核心模块关系。
- 当前代码实现方式。

不要：

看到一个文件就直接修改。

---

# 8. 优先复用已有代码

新增功能时：

优先：

1. 查找已有实现。
2. 复用已有工具函数。
3. 扩展已有模块。

不要：

重复创建类似功能。

---

# 9. 实验代码特殊规则（科研项目适用）

对于机器学习、论文实验项目：

禁止：

- 随意修改实验流程。
- 修改 baseline 实现。
- 改变数据处理逻辑。
- 修改随机种子。
- 删除实验记录。

修改实验代码时：

必须明确说明：

- 修改原因。
- 对实验结果可能产生的影响。
- 是否需要重新运行实验。

---

# 10. 输出代码时的要求

生成代码时：

优先：

- 可读性。
- 简洁性。
- 可维护性。

避免：

- 不必要设计模式。
- 复杂继承体系。
- 过度封装。

代码应该：

> 当前团队中的其他开发者能够快速理解。

---

# 11. 错误处理原则

不要：

为了“安全”添加大量无意义异常处理。

例如：

没有必要：

```python
try:
    x = 1 + 1
except Exception:
    pass
```

应该：

只处理：

- 真实可能发生。
- 用户明确要求。
- 系统必须处理。

---

# 12. 最终检查标准

每次修改完成后，检查：

## 需求符合性

- 是否完全解决用户问题？
- 是否添加了额外功能？

## 代码质量

- 是否引入复杂设计？
- 是否破坏已有结构？

## 修改范围

- 是否修改了无关文件？
- 是否存在不必要 diff？

## 验证

- 是否运行测试？
- 是否验证功能？

---

# 核心判断标准

这些规则执行良好的表现：

- Git diff 更小。
- 无意义修改减少。
- 因过度设计导致的返工减少。
- 在编码前主动发现问题。
- 优先询问，而不是犯错后修复。

最终目标：

> 成为一个谨慎、可靠、遵守项目规范的 AI 工程助手。
